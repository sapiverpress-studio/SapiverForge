Phase 1 systems checkpoint

Estimated learning time: 9–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
An AI product is a system, not a model. Quality depends on how models, prompts, data, APIs, retrieval, tools, permissions, evaluation, cost controls, reliability patterns and privacy rules fit together. Phase 1 readiness means you can reason about those parts as one architecture rather than as isolated features.

1. Start with the task, not the model

The first question is not “Which model should I use?”. It is “What task must the system perform, what inputs does it receive, what output is acceptable, and what failures matter?”.

Once the task is clear, you can decide which parts are deterministic, which need retrieval, and which genuinely benefit from model judgement.

2. Models generate; software controls

A language model predicts useful output from context. It does not automatically own your workflow.

Application code still decides when to call the model, which data to include, which tools are available, what actions are permitted and whether the result should be accepted.

3. Context quality matters

Prompting, retrieval and state all shape the context the model sees.

Good context is relevant, structured and appropriately scoped. More context is not always better: irrelevant material can increase cost, latency and confusion.

RAG adds external evidence, but retrieved content remains input and must still be treated according to its trust level.

4. Tools and agents need boundaries

An agent can choose among permitted tools and continue across several steps, but the surrounding system should keep permissions narrow and stopping conditions explicit.

High-impact actions can require human approval, and tool arguments should be validated before execution.

5. Reliability and security overlap

Timeouts, retries, fallbacks and circuit breakers keep failures contained. Least privilege, secret handling and validation reduce the consequences of misuse or mistakes.

Both disciplines ask the same architectural question: if this component fails, what can it affect?

6. Evaluation turns judgement into evidence

Before changing a prompt, model or workflow, define what success means and test against representative examples.

Separate retrieval failures, model failures and deterministic system failures so you fix the actual cause.

Regression tests protect behaviour that already works.

7. Cost and latency are design constraints

Every model call, retrieval, retry and tool invocation adds work.

The correct target is not “use the cheapest model” or “use the best model”. It is “meet the evaluated quality threshold with acceptable cost and response time”.

8. Privacy begins before storage

Data minimisation asks whether information needs to be collected at all.

Retention asks how long it should remain available. Memory should be purposeful, not an excuse to keep everything.

Logs, embeddings, backups and third-party services can all create additional copies that must be considered in the data lifecycle.

9. A strong architecture separates responsibilities

Reliable systems keep important boundaries visible.

Input
Deterministic rules
AI or retrieval step
Validation
Release or action

This separation makes systems easier to evaluate, secure, debug and change.

It also means a model can be replaced without redesigning every other part of the product.

Worked example: designing an AI support workflow

A customer sends a support question. The system first validates the request and identifies the account deterministically.

Relevant product documents are retrieved. The model receives the question plus the approved evidence and drafts an answer.

The system checks whether the answer is supported, whether a tool action is requested and whether that action is within the agent's permissions.

Low-risk answers can be returned. High-impact actions can pause for approval. Failures can fall back to source passages or a human queue.

Evaluation then measures retrieval quality, answer quality, action accuracy, latency and cost separately.

Phase 1 readiness

You are ready to move beyond foundations when you can look at an AI feature and explain where the model sits, where data comes from, what is deterministic, which permissions exist, what can fail, how quality is measured and how the system limits harm.

This checkpoint tests that system-level understanding rather than memorising definitions.

Key terms

System boundaryThe separation between components, data, permissions or responsibilities.
Deterministic stepA step whose outcome follows defined rules rather than probabilistic model judgement.
ContextThe information supplied to a model for the current task.
GroundingConnecting model output to supplied evidence.
Least privilegeGranting only the access needed for a task.
EvaluationMeasuring system performance against predefined criteria.
Graceful degradationKeeping reduced but useful functionality when full capability fails.
Data minimisationCollecting and processing only the data genuinely required.
