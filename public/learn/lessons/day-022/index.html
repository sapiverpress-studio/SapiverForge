Phase 1 · Day 22 · Failure-to-Eval Loop

Turning failures into evaluation tests

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
A failure becomes useful when you convert it into a test that can fail again. Trace the failure, isolate the cause, define the expected behaviour, add a representative evaluation case, then rerun that case whenever the system changes.

1. Do not fix a failure only once

If an AI system gives a bad result and you patch the prompt until that one example works, you have solved only the visible symptom.

The stronger approach is to preserve the failure as an evaluation case so future changes must continue to handle it correctly.

This turns debugging into cumulative system improvement.

2. Start from the trace

Use the request trace from Day 21 to identify where the failure began.

Was the wrong document retrieved? Did a deterministic permission rule fail? Did the model misuse correct evidence? Did a tool return unexpected data?

The evaluation case should test the failing layer, not just the final screen the user happened to see.

3. Capture the smallest useful reproduction

A reproduction case contains enough input and context to recreate the failure without dragging in irrelevant details.

For a RAG failure, that might include the question, the document set, the expected source and the expected answer behaviour.

Smaller cases are easier to understand, rerun and maintain.

4. Define the expected behaviour explicitly

A test needs a target.

For an exact extraction task, the target may be one value. For open-ended generation, define a rubric such as “must use the current policy, must not invent unsupported detail, and must escalate if evidence conflicts”.

A vague expectation such as “better answer” cannot support reliable regression testing.

5. Test the right layer

Different failures need different tests.

A retrieval regression test asks whether the correct source appears in the retrieved set. A generation test asks whether the model uses supplied evidence correctly. A tool test checks arguments, permissions and returned values.

One end-to-end score can hide which component improved or regressed.

6. Add nearby edge cases, not just the exact failure

A single failure often reveals a broader weakness.

If a system confused two policy versions, add tests for current versus archived documents, conflicting dates and missing version metadata.

This prevents overfitting the fix to one example while leaving the underlying pattern unchanged.

7. Keep holdout cases for honest measurement

If you repeatedly tune a system against the same examples, performance on those examples can improve without broader reliability improving.

Keep some evaluation cases separate from day-to-day prompt tuning.

These holdout cases provide a cleaner check that improvements generalise beyond the examples you actively used while making changes.

8. Regression tests should run after meaningful changes

Changes to prompts, models, retrieval settings, tools, policies or data can alter behaviour.

Rerun the relevant evaluation set after those changes and compare it with the previous baseline.

The important question is not only “did the new fix work?” but also “what previously working behaviour became worse?”.

9. Production failures should feed the evaluation set

Pre-release tests cannot predict every real user input.

When production monitoring reveals a meaningful new failure mode, remove unnecessary personal data, preserve the useful structure of the case and add it to evaluation.

This creates a feedback loop in which real use continuously improves the test suite.

Worked example: outdated policy retrieved

An employee asks for the annual-leave notice period. The system answers “two weeks” because retrieval selected an archived policy instead of the current four-week policy.

Trace retrieval
Define expected source
Add version edge cases
Fix retrieval
Run regressions

The primary regression test should assert that the current policy ranks above the archived policy for the relevant question.

A second test can check that archived documents are excluded when a current version exists. A third can verify that the answer states uncertainty if two current-looking sources conflict.

Only after retrieval passes should you judge whether the generated answer correctly uses the evidence.

Why this matters

AI systems change frequently: prompts evolve, models are replaced, indexes refresh and business rules change.

Without regression evaluation, every improvement can quietly damage something that already worked.

The failure-to-evaluation loop converts incidents into durable evidence about what the system must continue to do correctly.

Key terms

Reproduction caseA minimal example that reliably recreates a known failure.
Regression testA test that checks whether previously correct behaviour remains correct.
Expected behaviourThe explicit result or criteria a system must satisfy.
Holdout setEvaluation examples kept separate from active tuning to provide a less biased measurement.
Failure modeA repeatable pattern by which a system produces an undesirable result.
BaselineThe reference performance used to judge whether a change improved or worsened the system.
Edge caseAn unusual or boundary condition that can expose weaknesses missed by common examples.
GeneralisationPerformance that carries beyond the exact examples used during tuning.
