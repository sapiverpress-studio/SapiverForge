Phase 1 · Day 21 · Request Tracing

Tracing an AI request end to end

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.
Core mental model:
When an AI result is wrong, slow, expensive or unsafe, trace the request through the whole system instead of blaming the model first. At each boundary ask: what came in, what decision was made, what evidence or tool was used, what controls applied, and what left the boundary?

1. Draw the request path before diagnosing it

An AI feature usually contains more stages than the user can see.

A request may pass through authentication, input validation, deterministic rules, retrieval, a model call, tools, output validation, approval and storage before the user sees a result.

Tracing means following that path in order and identifying which component produced each important decision or transformation.

2. Start at the input and trust boundary

Record what entered the system and where it came from.

User text, uploaded files, retrieved documents and third-party API responses have different trust properties. None should silently gain authority merely because a model can read them.

At this stage, check authentication, permissions, expected format and whether unnecessary personal data is being collected.

3. Identify deterministic decisions

Some steps should have one predictable answer.

Examples include checking whether an account exists, comparing a refund amount with a fixed threshold, validating a date format or enforcing a permission rule.

If one of these steps fails, changing the model prompt is the wrong fix. The deterministic rule or its data needs attention.

4. Trace retrieval separately from generation

For a RAG system, first inspect what the retrieval layer returned.

If the correct evidence never reached the model, the failure is upstream of generation. If the correct evidence was present but the answer misused it, the model, prompt or answer-validation stage needs investigation.

This separation turns a vague “AI got it wrong” report into a specific engineering diagnosis.

5. Make tool calls visible

When an agent uses tools, record which tool was selected, which arguments were sent, what permissions applied and what the tool returned.

A model may choose the wrong tool, construct invalid arguments or correctly call a tool that itself returns bad data.

These are different failure modes and should not be collapsed into one model-quality score.

6. Validate before release or action

The model's output is not automatically the final product.

Structured output can be checked against a schema. Claims can be checked against retrieved evidence. Proposed actions can be checked against business rules and permissions.

High-impact actions can stop at a human approval gate rather than executing immediately.

7. Trace latency and cost by stage

End-to-end response time may include database calls, retrieval, several model calls, tool use and retries.

Record stage timings and usage separately so you can see what is actually expensive or slow.

A three-second delay caused by retrieval will not be fixed by choosing a faster model.

8. Record failure handling as part of the trace

A reliable trace should show timeouts, retries, fallbacks and circuit-breaker decisions.

If the preferred model times out and the system falls back to source passages, that fallback is part of the successful system behaviour.

Observability should explain not only what failed, but also which recovery path ran afterward.

9. Finish with the data lifecycle

The request is not necessarily finished when the response appears.

Ask what is stored afterward: conversation content, logs, tool results, embeddings, evaluation samples or analytics.

Each stored copy should have a purpose, an access policy and a retention rule. Tracing data flow therefore connects reliability and debugging with privacy.

Worked example: diagnosing a wrong leave-policy answer

An employee asks, “How much notice do I need to give for annual leave?” The assistant answers “two weeks”, but the current policy says four weeks.

First inspect retrieval. If it returned an old two-week policy, the model may have used its supplied evidence correctly and the real fault is stale indexing or document filtering.

If the current four-week policy was supplied but the model answered two weeks, inspect prompting and generation.

If the draft correctly said four weeks but a later formatting or templating step changed the value, the failure happened after the model.

The trace identifies the component to fix and creates a regression test for the same scenario.

Why this matters

Phase 1 introduced models, APIs, retrieval, agents, automation, security, evaluation, cost, reliability and privacy.

Request tracing is where those concepts become one practical diagnostic method.

If you can follow a request across boundaries and explain where decisions, evidence, permissions and failures occur, you are reasoning about the AI product as a system rather than a black box.

Key terms

TraceA record of the important stages, decisions, calls and results in a request.
SpanA timed unit of work inside a trace, such as retrieval or a model call.
Trust boundaryA point where data or authority crosses between components with different trust levels.
Upstream failureA failure earlier in the request path that affects later stages.
PostconditionA condition that should be true after a step completes.
ObservabilityThe ability to understand system behaviour from traces, logs, metrics and related signals.
Regression testA test that checks whether a previously solved failure remains solved.
Data lifecycleThe path data takes through collection, use, storage, access and deletion.
