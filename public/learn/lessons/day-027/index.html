Phase 1 · Day 27 · Change Control

Changing AI systems safely

Estimated learning time: 8–10 minutes.

Ready to listen. Speed: 1.00×.

Core mental model:
Every change to an AI workflow is a new hypothesis, not an automatic improvement. Version the change, test it against known cases, expose it gradually when risk justifies that, compare outcomes with a baseline, and keep a clear rollback path. Change one meaningful variable at a time when practical so you can tell what caused the result.

1. A working system can regress

A prompt edit, model upgrade, retrieval change or new tool can improve one class of cases while making another worse.

That is a regression: behaviour that previously met the required standard no longer does.

Change control treats existing good behaviour as something to protect, not something to assume will survive.

2. Version the parts that affect behaviour

To diagnose a change, you need to know what actually ran.

Useful versions can include prompts, model identifiers, retrieval settings, validation rules, tool definitions and release policies.

A production record should identify the behaviourally important configuration.

3. State the expected improvement before changing

A change is easier to evaluate when its purpose is explicit.

For example: “This retrieval change should reduce unsupported answers on policy questions without increasing response time beyond an acceptable amount.”

That gives you a success condition and prevents vague post-hoc claims that any different result is an improvement.

4. Run regression tests before release

Use evaluation cases built from previous failures and important normal cases.

A new version should be tested against both the problem it is meant to solve and behaviour you do not want to lose.

Passing the new target case while failing established cases is not a clean improvement.

5. Separate comparison from intuition

Compare the candidate with the current baseline using the same evaluation set and metrics.

Look at quality, failure categories, latency, cost and escalation behaviour rather than a few impressive examples.

Side-by-side evidence makes trade-offs visible.

6. Roll out according to risk

Not every change needs the same release process.

A low-risk wording change may be released after tests. A change affecting payments, permissions or high-volume decisions may justify a limited rollout or additional human review first.

The rollout method should reflect consequence and reversibility.

7. Define rollback criteria in advance

A rollback is easier when the trigger is decided before pressure builds.

Examples include a sustained rise in error rate, material increase in human overturns, a safety gate failure or cost beyond an agreed limit.

Keep the previous known version available so recovery does not depend on reconstructing it during an incident.

8. Monitor after the change

Pre-release evaluation cannot reproduce every production condition.

Use Day 26 monitoring signals to compare the new version with its baseline after release.

Watch for unexpected distribution changes, new exception patterns and outcome degradation, not just the metric the change was designed to improve.

9. Record the decision, not just the code

A useful change record says what changed, why, what evidence supported release and what happened afterward.

This creates organisational memory and makes later diagnosis faster.

It also helps prevent repeatedly trying changes that previously failed for known reasons.

Worked example: changing the model behind a support classifier

A team wants to replace its current classifier with a newer model that appears more accurate on difficult complaints.

Define target
Version candidate
Run regression set
Compare baseline
Limited rollout
Monitor or rollback

The team first states the target: improve difficult-case routing without increasing false high-risk escalations.

Both versions run against the same historical evaluation cases. The candidate improves difficult cases but also increases escalations slightly, so the team releases it to a limited share of eligible traffic and monitors human overturns.

If overturns cross the predefined threshold, traffic returns to the previous version while the failure cases are added to the evaluation set.

Why this matters

AI systems can change behaviour when prompts, models, data, tools or policies change.

Safe iteration requires behavioural versions, comparison evidence, release criteria, monitoring and a recovery path.

The aim is to improve the system without sacrificing reliability already earned.

Key terms

RegressionA loss of behaviour or quality that previously met the required standard.
BaselineThe current reference version or performance used for comparison.
Candidate versionA proposed configuration being evaluated before or during controlled release.
Change controlThe process for evaluating, approving, releasing and tracking system changes.
Limited rolloutReleasing a change to a restricted portion of eligible use before wider adoption.
RollbackReturning to a previous known version when a new change performs unacceptably.
Rollback criterionA predefined condition that triggers or strongly indicates reversal of a change.
Behavioural versionAn identifier for the important configuration that determines how a workflow behaves.
